# MultAIBall work log

Append-only. Each entry: where in the codebase the work was, the options on the table going in, what was chosen and which project priorities decided it, what comes next. Priorities, in the order they are applied: (1) the promise is the payload, browser and Python send the same body from the frozen run; (2) usable by people fluent in spreadsheets and not in LLM APIs, so fewer controls and more handholding, never more granularity; (3) the stack a human can read end to end, so dependencies over rolled-own code, and no machinery built for a broader product than this one; (4) each provider is its own authority about its own models; nothing the app "knows" is a gate. Context for all of it: `FULL-CONTEXT-20260913.md`.

## 2026-09-14 (a): reading alfresh's provider layer and choosing what to take

**Where.** `src/core/types.ts` (rewritten by the prior session), the new `src/core/providers/{shapes,presets,guidance}.ts`, `exceptions.json`, `scripts/sync-models-dev.mjs`, `src/data/models-dev.json`. Nothing else consumes the new types yet: `tsc` reports 116 errors across 24 files; vitest still passes 158 because it does not typecheck.

**Read.** `../codexd/alfresh/docs/HANDOFF-LLM-API-STACK-ADVICE-20260914.md` and `../codexd/alfresh/docs/PROVIDERS.md` (both granted). Alfresh's layer is: a shape JSON per wire protocol, a provider JSON per vendor with vocabulary deltas, a composed `EndpointContract` per endpoint, per-provider discovery sources writing per-model guidance, a hand-written quirks overlay with a note and an expiry per entry, one form engine (`draft.ts`) with Basic/Advanced/Raw tiers driven by a parameter vocabulary with roles and `when` rules, and a Node probe rig that sends the app's own request. Its advice doc says explicitly: do not build that machinery for a two-or-three-vendor app; at that level, one shape file per protocol, one provider file per vendor, models.dev for temperature and effort values, a hand-written exceptions file, and a probe rig are the whole thing.

**Options going in.**
A. Vendor alfresh's `contracts/shapes/*.json`, `contracts/providers/*.json`, `compose.ts`, `knowledge/*`, and `draft.ts`, and build MultAIBall's four presets as deltas on their shapes. Buys a tested vocabulary engine and their discovery translators. Costs: the vocabulary, tiers, roles, `when` rules, and delta composition exist to render dozens of parameters across eight providers with per-surface presentation policies; this app exposes four parameters and a key/value box. Every line of that engine would be maintained here to serve controls the product refuses to show. Violates priority 3 and the alfresh doc's own §1.
B. Take alfresh's architecture and its measured rules, not its code: contract (per endpoint, hand-written, never per model) separate from guidance (per model, advice, never a gate) separate from the user's values; hand-written exceptions with provenance and expiry; `require_parameters` on by default for OpenRouter; temperature starts unset unless a source says the model accepts it; the output-length concept found by role with the spelling per endpoint (and per model on OpenRouter); response-format defaults to schema only when a contract exists and no source refuses, otherwise nothing; a probe rig that sends the app's own body. Implement at this app's size in TypeScript: `presets.ts` is the contract, `guidance.ts` is the guidance, `SharedParams` plus `ModelSettings` are the values. This is what the prior session began.
C. OpenRouter only (alfresh's level A). Simplest possible provider layer. Rejected earlier by the owner: native OpenAI, native Anthropic, and any Chat Completions endpoint are launch requirements.

**Chosen: B.** Priority 3 decides it against A; the owner's provider decision rules out C. Sub-decisions where alfresh's stack does something this app will not copy, each with the priority that decided it:

- Alfresh reads the *vendor's* models.dev temperature record for a `vendor/model` id on OpenRouter (Opus 5 through OpenRouter accepts temperature only at its default; the union lists the name). The prior session's `guidance.ts` copied that inference. Removed here: the owner's rule is that OpenRouter's models are OpenRouter's, described by OpenRouter's catalog, and nothing learned about a vendor's native model transfers (priority 4). Consequence for the newcomer: temperature set on a run that includes `anthropic/claude-opus-5` produces a visible 400 on that model's rows with the vendor's message; the handholding is a per-model "turn temperature off for this model" on the review and results screens, not a silent difference between what two models were sent (priority 1 over priority 2, and the alfresh doc's own §4 "offer the one-click way out next to the error").
- Alfresh's vocabulary carries Basic/Advanced tiers per parameter. Here there is no Advanced tier: four shared controls, applied per model only where guidance says the model accepts them, plus the per-model key/value box. The review screen reports per model and per parameter: sent or omitted, the value, the reason, the source (`ParamReport` in `types.ts`).
- Alfresh's `when` rules (Anthropic `thinking.type: enabled` forces `temperature: 1`) are not needed: this app does not expose thinking budgets; effort is the only reasoning control and only where the model lists effort values.
- Three-state booleans: no boolean parameter is exposed; the key/value box carries any the user wants, literally.
- Temperature default: unset (alfresh measured that prefilling 0 put a 400 on every Claude 5 and OpenAI reasoning model). The previous default of 0.7 in `state.ts` goes. A newcomer who leaves it unset gets each provider's own default, which is the honest default.
- Output length default: 2048 (alfresh's), sent on every model under that endpoint's spelling, clamped to a reported ceiling; Anthropic requires it and the others accept it.
- OpenAI ids that are Responses-only (`*-pro`, `*-codex`, `gpt-live-1`, measured by alfresh 2026-09-14) are dropped by name in the OpenAI catalog filter along with audio, search, and image ids, because this app speaks Chat Completions only and a 404 on those would look like a bug.
- The probe rig comes later, as `scripts/probe/`, a Node script that builds bodies through the app's own `build.ts` and writes results to `tmp/`; candidates are promoted into `exceptions.json` by a person. The `tmp/verify/probe*.sh` scripts from 2026-09-13 are its seed.

**Housekeeping decided.** `zod` removed from `package.json` (unused). `npm run sync:models-dev` added. `src/types.ts`, `src/core/provider-config.ts`, `src/core/config-shapes.ts`, the old `src/core/providers.ts`, `vendor/providers/`, and `scripts/sync-providers.mjs` are deleted as the new modules replace their consumers. LiteLLM fetching in `pricing.ts` goes; models.dev carries price for OpenAI and Anthropic, OpenRouter's catalog for OpenRouter, nothing for custom.

**Next.** Phase 1, core against the frozen run, in this order because each consumes the previous: `providers/build.ts` (preset + catalog model + shared values + model settings + contract → `FrozenModel` with body skeleton and report); `partition.ts` and `examples.ts` (roles, sparsity partition, constant block); `freeze.ts` (the `FrozenRun`); `render.ts` (frozen run + coordinate → system, prompt, body, body string); `api.ts` rewritten to send a rendered body and return a `CallRow` with the body hash, non-streaming only; `run.ts` rewritten to iterate coordinates; `catalog.ts` replacing `ui/data.ts` and the old list parsing; `export.ts` (long table and completed dataset, no pandas parity); `py.ts` and the Python runtime consuming the frozen run; the three invariant tests. ## 2026-09-15 (a): the whole stack, not only providers; the five open trade-offs and the picks

Re-read against the September 13 material (the research handoff and `FULL-CONTEXT-20260913.md`): users, the dataset flow, worked examples, the partition, the completed dataset, the Python promise. Nothing there changes the provider layer beyond what (a) recorded. The five items below are trade-offs, not invariants; the owner is the source of truth and can overrule any of them. Each is built as picked unless he does.

1. **Results survive a reload.** One IndexedDB store keyed by run id, the frozen run written at freeze, one small row appended per completed call, no indexes, no versions, readers tolerate unknown shapes. No resume of execution. Overrides `ARCHITECTURE.md`'s "never persist results", which was aimed at whole-blob rewriting and schema churn; per-call append has neither. Priority 2 (paid calls are not lost) over the old rule; priority 3 kept by having no schema to migrate.
2. **Example input = the item template rendered with the example row.** Faithful few-shot form; repeats any instruction text in the item template once per example, visible in the token count. Alternative (bound columns as name: value) rejected for method fidelity (priority 1 of the analyst's artifact being what a reviewer expects).
3. **Temperature default unset.** Not sent is the one value the app cannot be wrong about; guidance would suppress a prefilled value on refusing models anyway. Priority 2's handholding is the shared-controls screen explaining what unset means.
4. **Bundle cases as `cases.csv` beside `experiment.json`.** Readable by a spreadsheet and by Python's csv module; values are already strings. JSON-embedded rejected for a 240 MB file at the ceiling; Parquet rejected for the pyarrow install. Priorities 2 and 3.
5. **UI: vanilla TypeScript with one store, no framework.** Six screens. The fragility in the current `app.ts` is mutations forgetting which renderers to call; a `set(patch)` store that notifies regions fixes that in forty lines. Priority 3.

Also decided while building: when a sheet declares no output columns, the completed-dataset export appends the parsed fields as new columns; the sweep flow warns above 1,000 cases and blocks above 20,000; examples are excluded from execution by default and a user moves a row between examples and targets in the partition editor (no holdout scoring in v1).

**Options that came up while building, and the picks.**

**Where.** `src/ui/store.ts` (one store; `update(fn)` mutates, saves, notifies), `src/ui/model.ts` (derived state and the stage gates), `src/ui/actions.ts` (everything a screen may ask for: catalog, sheet, freeze, run, pause, resume, rerun missing, saved runs, exports, run files), `src/ui/screens/{prompt,output,models,settings,review,results}.ts`, `src/ui/app.ts` (composition root, 80 lines). **Options and picks.**
- Results table: virtualization (the handoff's `regular-table`) vs pagination. Fifty rows a page with filters (text, status, model) and a detail dialog per row. A page is the simplest way to guarantee the DOM never holds more than a screenful, it is what a spreadsheet user expects, and it adds no dependency (priority 3). Virtualization is a later swap behind the same `renderTable` if scrolling through 20,000 rows ever matters more than filtering them.
- Example-selection UI: alfresh's navigator vs a paged table of rows with a three-way choice per row (worked example / run / skip) inside a collapsed details block, with a "back to the sheet's own split" reset. The default needs no interaction; the editor exists for the analyst who wants a subset (priority 2 without adding a surface to the default path).
- Per-model settings: an Advanced tier vs a gear per selected model opening a dialog with the response-format override, an extras JSON box, and the OpenRouter routing fields. No tier; four shared controls stay the whole main surface.
- Review: the frozen run itself is rendered (per model: the parameter report with reason and source, the context check, the first call's body). Freezing on entering the screen is cheap (one token count) and means what the user reads is the object the run will execute, not a description of it (priority 1).
- Persistence: every run is written to IndexedDB at freeze and per completed row (`runstore.ts`); the results screen lists saved runs (Open, Delete) and offers "Run the missing calls" for any run whose rows are not all ok, under the same run id. That is resume without resuming execution state. Run files (zip of frozen run + rows) replace the old whole-state backup; settings and templates stay in localStorage.
- A real defect found by the e2e suite: Vite's dev optimizer discovered `gpt-tokenizer` when the tokenizer worker was first created (only when examples exist to count) and forced a full reload that dropped the session's sheet. Fixed by pre-including the worker's dependency in `vite.config.ts` and warming the worker at startup. Production builds were never affected.

## 2026-09-15 (e): the UI was built for people who already know the concepts; overhaul

**Owner's report, verbatim in substance.** Uploading a sheet produced a 30-row table of dropdowns all reading "Input (sent when the prompt uses it)", with identical hints, that had to be set one by one; the prompt fields sat at the bottom; "choose which rows are…" meant nothing; the output-format screen was busy and overwhelming for a single prompt; one shared parameter set across models is fine (one provider at a time) but "sent only to models that list the chosen level" makes a shared effort of `medium` mean different things per model, which is wrong. The app must be pedagogical: rows and columns are known, payloads and structured output are not.

**Options going in.**
A. Keep the role-per-column table, improve labels and hints. Cheapest; still 30 decisions for a two-column task.
B. Ask two questions with checklists and sample values ("What should the model read?", "What should the model fill in?"), guess the answers from the sheet (longest text column reads; partly filled columns get filled), treat every other column as kept-not-sent by default, generate the per-row template from the chosen columns, and pre-fill the answer format from the output columns' existing values. Reference vs metadata disappears from the surface (both are "kept, never sent"); the role model underneath is unchanged.
C. A guided one-question-per-screen wizard of ten steps. Most hand-holding; also the most clicking, and the sheet already answers most questions.

**Chosen: B**, with the screens reordered so the user reads: your data, your instructions, the answer format, models, settings, check, results. Priority 2 decides it; the underlying `roles` and `partition` (priority 1's boundary) are untouched, so the invariant tests still hold.

**Effort normalization.** A shared level is mapped per model to that model's own list: "less thinking" sends the model's lowest listed level, "more thinking" its highest, default sends nothing; an exact level typed in the per-model extras still wins. The review screen shows the value each model gets. This is a value the app chooses on the user's behalf, which the alfresh rule forbids; here the user's choice was relative ("less"/"more"), the mapping is deterministic and visible, and the alternative (a shared absolute level silently omitted on models that spell theirs differently) is the incoherence the owner objected to. Temperature gets words too (Default / Focused 0.2 / Balanced 0.7 / Creative 1.0) with an exact field under "more options".

**Answer format defaults.** Sheet with output columns: one field per output column, type guessed from the filled values (numbers → number or whole number; up to eight distinct short values → choices; else text), editable. Sheet with no output column: the user names a new column ("answer" by default) and the model fills it. Single prompt and sweep: plain text unless the user adds fields. Parser follows automatically (fields → JSON to columns; no fields → keep the text); rationale-first, strict JSON and the parser picker move under "more options".

**Next.** Implement, re-run the suites, then write `HANDOFF-PROVIDER-NORMALIZATION-AND-UI-20260915.md` on the trade-offs the owner named: per-model controls vs shared, what normalizes cleanly and what does not, progressive disclosure, showing the payload.
